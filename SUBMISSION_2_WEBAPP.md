### Project description — required, 100–200 words

Word count: **183**. Verify before pasting.

```
QUANTUM NEGATIVE is a web app that turns a text prompt into a short film, a
stereo score and a poster, generated by driving the Moth Atlas API.

The design decision behind it is attribution. Plenty of generative tools show you
an output; this one also tells you what made it. Every run reports, per stage,
whether a real Atlas engine produced that layer or whether a local fallback did,
and why. The pipeline has genuine hardware boundaries — the account can run some
engines on a physical QPU and others only in emulation — so the app surfaces those
boundaries instead of hiding them behind a spinner.

The interface exposes the quantum creative budget: the measured values that
decided the melody, colour and structure, alongside a provenance table naming the
engine behind every choice. Generation runs as a background job with real stage
progress rather than a fake progress bar.

It is standard-library Python with no build step: `python webapp.py`, then open
the page. A playable mode at `/game` develops a latent photograph from qubit
marginals.
```

### Technical description — required, 50–100 words

Word count: **84**. Verify before pasting.

```
A single-file Python web app using only the standard library — no framework, no
build step — serving generated media from an in-process job runner with real
stage-level progress. It talks to the Moth Atlas REST API for quantum execution
and media engines, and a locally written nine-qubit statevector simulator provides
an offline path so the app runs without credentials. Engines used: qpixl-v1
(encode/measure/decode on ibm_fez and Aer), blur-v1, telablur-v1 and
retrocausal-echo-v1.
```

## The one honest risk with this category

**"Most web app submissions are hosted"** — you said that yourself, and you are
probably right that a live URL is expected here in a way it is not for the
notebook.

We are submitting a **run-locally** app, which is weaker for this category
because a judge cannot click it. Two ways to handle it:

1. **Leave the Demo URL blank** and rely on the video showing the app running.
   Honest, and the video does show it. But a judge who wants to try it cannot.
2. **Host it.** This is a genuine option: the app is a single standard-library
   Python file with no build step, so it can run on any free Python host. The
   blocker is that it needs the Atlas API key as a server-side environment
   variable, and a public instance would let anyone spend the account's credits.

I would not put a shared key on a public URL.

**Better option 3, if you want a live demo:** host a version that runs on the
**local simulator** with no key, and keep the Atlas path as something the video
demonstrates. That gives a judge something clickable and costs nothing, and the
app already supports it — `LocalBackend` exists precisely so the app runs without
credentials. Be honest in the description that the hosted instance is the offline
path.

Tell me if you want that, and I will build and verify the hosted variant rather
than guess at it.
